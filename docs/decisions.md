# Архитектурные решения и альтернативы

## 1. Очередь в PostgreSQL

**Контекст:** статус заявки и задача её обработки должны фиксироваться согласованно.
**Решение:** jobs в основной БД, PostgreSQL row locks и SKIP LOCKED.
**Плюс:** меньше инфраструктуры, общая транзакция для состояния и постановки работы.
**Цена:** polling и конкуренция за БД; размер очереди и задержки надо измерять.
**Альтернатива:** внешний брокер с outbox publisher и отдельным контролем доставки. Для учебного MVP эта
инфраструктура увеличивает объём эксплуатации; переход оправдан реальной нагрузкой и требованиями.

## 2. Политика, ML и LLM разделены

**Контекст:** учебная ML-модель обучена на синтетических метках и не валидирована для выдачи кредита.
**Решение:** правила определяют бизнес-исход; ML даёт отдельную оценку аналитику; LLM опционально объясняет факты.
**Плюс:** недоступность экспериментальной модели не останавливает основной сценарий.
**Цена:** система пока не сравнивает долговременное качество политик на реальном портфеле.
**Следующий шаг:** журнал shadow-прогнозов, версионированные данные наблюдений и независимый процесс допуска модели.

## 3. Прогноз из сохранённого снимка

**Контекст:** анкета может меняться, признаки скоринга обогащены внешними фактами.
**Решение:** adapter читает последний ScoringResult, возвращает его id и время, не делает запись.
**Плюс:** понятный источник признаков, повторяемый расчёт и отсутствие побочных эффектов.
**Цена:** при смене весов текущий прогноз будет другим; версию и hash надо сохранять отдельно,
если требуется постоянная история прогнозов. Текущая ручка такой историей не является.

## 4. JSON вместо pickle

**Контекст:** Logistic Regression требует только масштабирования, скалярного произведения и sigmoid.
**Решение:** экспорт средних, scale, coefficients, intercept, threshold и диапазонов train в строгий JSON.
**Плюс:** нет sklearn в API-образе, нет десериализации исполняемых Python-объектов; легко проверить паритет.
**Цена:** exporter и inference надо поддерживать вместе. Контракт подходит этой модели, не произвольным пайплайнам.
**Альтернатива:** ONNX при усложнении моделей; model server при потребности в независимом масштабировании.

## 5. Ограниченный пакет и атомарная валидация

**Контекст:** API полезен для сравнения нескольких сценариев, но не должен принимать бесконечный список строк.
**Решение:** от 1 до 100 строк на batch; порядок сохраняется, неверная строка отклоняет весь запрос.
**Плюс:** простой контракт и предсказуемая верхняя граница работы одного запроса.
**Цена:** крупные задания нужно дробить; асинхронный batch service здесь не реализован.

## 6. Покрытие как сигнал, а не цель само по себе

**Контекст:** важно обнаруживать ошибки поведения, а не увеличивать счётчик тестов.
**Решение:** branch coverage всего `app`, CI-порог 80%, плюс проверки инвариантов и пользовательские e2e.
**Плюс:** видны пропущенные ветви, а ключевые гарантии проверяются по результату.
**Цена:** coverage не обнаружит неверный assertion или неизвестный сценарий; нужны review и работа с рисками.

## 7. SQLite для быстрого локального стенда

**Контекст:** у разработчика может отсутствовать Docker/PostgreSQL.
**Решение:** изолированный development launcher и отдельная PostgreSQL-suite в GitHub Actions.
**Плюс:** UI/ML-проверки воспроизводятся локально; логи остаются после остановки процессов.
**Цена:** SQLite не эмулирует блокировки PostgreSQL. Успех локального smoke не заменяет миграции и CI на PostgreSQL.

**Дата:** 22.10.2026. **Заморозка кода:** 26.10.2026, 10:00 МСК (точный час сдачи не подтверждён).

**Основа решения:**

- запуск тестов, сборки фронтенда и стека без Docker;
- три независимых экспертных разбора: кредитный риск и продукт; архитектура, безопасность и
  эксплуатация; UX и прохождение сценария глазами жюри.

## 1. Итог в трёх фразах

1. **Фундамент сильный.** Машина состояний, очередь задач в БД, отказоустойчивые интеграции и объяснимый
   скоринг работают. Это подтверждено запуском: 54 теста зелёные, все шесть демо-персон доходят до решения.
   Время до решения — 6–7 с при `PIPELINE_STEP_DELAY_S=0.3`; с настройками compose по умолчанию медленнее.
2. **Сквозной путь из кейса обрывается на решении.** Клиент не может принять предложение, подписать договор
   и получить деньги. Аналитик не может решить по заявке на ручном рассмотрении. Это два главных пункта
   критерия 1 «Целостность».
3. **Риск-эксперт найдёт уязвимые места в кредитной логике.** Нагрузка считается к выручке, а не к прибыли.
   Выручке из «любого файла выписки» банк верит на слово. Текущая просрочка до 60 дней не мешает
   автоодобрению. Закрыть это дешевле, чем защищать.

## 4. Кандидаты на дифференциацию

Базовые идеи из исследования команды есть почти у всех: объяснимое решение, what-if, два экрана,

заметно более глубокая версия.

**Шкалы (1–5):**
- **Боль** — насколько реальна, с источником.

- **Реализм** — примет ли это риск и продукт Альфы.
- **Риск** — опасность для основного пути (5 — безопасно).

## 6. Что вырезаем

- **Шаги 5 и 6 плана в README: ML-скоринг и ассистент на языковой модели.** Честно сделать их не успеваем: ML на
  синтетике риск-эксперт разберёт за минуту, а LLM требует отдельного профиля Ollama и проверки на
  «обычном ПК». Переносим в «Развитие» с объяснением, куда они встраиваются: скоринг через тот же интерфейс
  `ScoreResult`, LLM — только для объяснения по готовым фактам. В THIRD_PARTY_NOTICES явно указываем, что
  LLM не используется.
- **Публичный стенд.** Желателен, но не обязателен, а бесплатные варианты требуют регистрации и карты.
- D, H, I, J — в «Развитие».
- Рефакторинг и стиль кода не трогаем.

## 9. Утверждённые изменения (22.10)

1. Docker локально нет, поэтому первым делом — CI в GitHub Actions:
   - pytest на PostgreSQL;
   - сборка фронтенда;
   - проверка расхождения OpenAPI с кодом;
   - сборка и подъём compose с ожиданием готовности, дымовой сценарий «демо-вход → заявка пекарни →
     одобрено», затем остановка.
2. Порядок: P0.3 (привязка компании — по реальному правилу владения) → CI → P0.1 → P0.2 → P1.8 →
   P1.5 + P1.6 → B → G вместе с B5 → лента новостей → A с воспроизведением → C → E.
   P0 — к концу 24.10.
3. После каждого пункта P0 и каждого дифференциатора — код-ревью изменений и исправление найденного.
   25.10 — только сквозная проверка, документация, полное ревью ветки против кейса и чек-листа сдачи,
   релиз-кандидат.
4. Документация обновляется вместе с каждой функцией: architecture, state-machine (signing, issued,
   expired), data-model, openapi.json, коллекция, точные цифры по персонам в README.
5. Лента показывает новости: синтетический набор с тегами по ОКВЭД, продукту и статусу, с пометкой
   «смоделировано», разная у разных персон.
6. Контрпредложение «другой продукт» реализуем. Если окажется большим — описываем как допущение.
7. Релиз: тег `rc` вечером 25.10. Слияние в `main` и финальный тег — до заморозки, по отдельному
   согласованию. Доступ для `alfa-hack-2026` — проверить перед сдачей.

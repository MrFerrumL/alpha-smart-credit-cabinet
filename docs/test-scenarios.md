# Тестовые сценарии

Сценарии для проверки «Потока» целиком: сквозные пути по каждой роли, отказоустойчивость, негативные и ролевые
случаи. У каждого сценария указаны точные входные данные, ожидаемый результат и автотест, который это
доказывает. Если автотеста нет, так и написано: «проверяется вручную».

## Как подготовиться

```bash
git clone https://github.com/donaldtrumpdev-commits/alpha.git
cd alpha
docker compose up --build
```

- Кабинет — http://localhost:8080, Swagger — http://localhost:8000/api/docs, эмулятор внешних систем —
  http://localhost:8001/docs. Дождитесь, пока все сервисы станут «healthy»; проверка стенда одной командой:
  `python scripts/smoke.py`.
- Вход: на странице входа вход в один клик под любой тестовой учётной записью. Пароль у всех `demo1234`
  (для `POST /api/auth/login`). У каждой вкладки браузера свой вход, поэтому клиента и аналитика удобно открыть
  рядом. Список демо-учётных записей и вход по паролю проверяют
  `test_api.py::test_demo_accounts_cover_all_scenarios` и `test_api.py::test_password_login`.
- Как подать заявку: «Подобрать кредит» → цель, сумма, срок → «Оформить» у продукта → анкета по шагам → согласие на
  запрос в БКИ → «Отправить в банк». Данные компании и выручка из ФНС подставляются сами.
- Сценарии независимы, но стенд помнит всё, что вы делали: заявки копятся (их видит симулятор политики), а ИНН
  `0077070071` для `new@demo.local` подключается один раз. Чтобы вернуть чистое состояние:
  `docker compose down -v && docker compose up --build`.
- Сбои источников включаются командами из раздела «Отказоустойчивость». Перед сценариями, где сбоя быть не
  должно, снимите их: `{"source":"all","mode":"none"}`.

Имена автотестов даны в виде `файл::тест`; файлы лежат в `backend/tests/`. Запуск — в конце документа.
Всего в проекте 144 автотеста на backend и 12 сценариев в браузере (`e2e/`).

### E2E-01. Одобрение, подпись кодом, выдача

- **Роли:** клиент-директор (`bakery@demo.local`, Ольга Северова, ООО «Северная пекарня»).
- **Шаги:**
  1. «Пополнить оборотные средства» → «Экспресс-оборот», 3 000 000 ₽, 12 мес. Выручку в анкете оставить как
     подставилась (4,5 млн). Согласие на запрос в БКИ → «Отправить в банк».
  2. Следить за статусом на странице заявки: проверка данных → проверка компании → оценка → решение.
  3. «Принять и перейти к договору», отметить ознакомление, «Подписать кодом».
  4. Код показывается прямо в окне подписания. Сначала ввести неверный код, затем верный.
  5. Подождать несколько секунд, открыть «Мои кредиты».
- **Ожидается:**
  - Примерно за 10 с статус «Одобрено»: 3 000 000 ₽ под 22,9 %, у решения есть объяснение; три проверки
    (ЕГРЮЛ, ФНС, БКИ) со статусом «ok», сырые ответы источников клиенту не отдаются.
  - Номер договора `КД-<год>-<номер заявки, 6 цифр>`, в договоре хеш условий из 64 символов.
  - Неверный код: ошибка «Осталось попыток: 2»; верный код подписывает договор. Повторное использование кода
    отклоняется. После подписи заявку отозвать нельзя.
  - Статус «Деньги зачислены»; в «Мои кредиты» кредит на 3 000 000 ₽, остаток 3 000 000 ₽, график из 12
    платежей по одному в месяц, остаток после последнего платежа 0. Пришло уведомление «деньги зачислены».
  - Код подписи нигде не виден в уведомлениях.
- **Автотесты:**
  `test_pipeline.py::test_reliable_company_is_approved_automatically`,
  `test_signing.py::test_full_path_from_offer_to_loan`,
  `test_signing.py::test_notifications_can_be_marked_read`,
  `test_pipeline.py::test_financials_prefill_from_tax_data` (подстановка выручки 4,5 млн из ФНС);
  на поднятом стенде — `scripts/smoke.py` (вход → заявка → одобрение).

### E2E-03. Бухгалтер готовит — директор подписывает

- **Роли:** главный бухгалтер (`buh@demo.local`, Елена Счётова) и директор (`bakery@demo.local`) одной компании.
- **Шаги:**
  1. Бухгалтер готовит и отправляет ту же заявку, что в E2E-01.
  2. После одобрения бухгалтер видит предложение, но не кнопки «Принять», «Отказаться» и «Подписать»; у него
     есть «Передать руководителю на подпись».
  3. Бухгалтер нажимает «Передать руководителю на подпись».
  4. Директор в своей вкладке видит уведомление «запрос на подпись» с именем Елены Счётовой, принимает
     предложение и подписывает кодом.
- **Ожидается:**
  - После передачи бухгалтер видит «Предложение передано руководителю … уведомление уже в кабинете руководителя,
    осталось принять предложение и подписать договор»; повторная передача — отказ (409), директор тоже не может
    «передать» сам себе (409).
  - В журнале событие «передано на подпись» от имени бухгалтера.
  - Подпись фиксирует основание: «руководитель по ЕГРЮЛ: Северова Ольга Николаевна». Итог — «Деньги зачислены».
  - Пользователь с флагом права подписи, но не руководитель по ЕГРЮЛ, принять и подписать не может (403 с
    именем руководителя по ЕГРЮЛ), может только передать; запрос уходит директору, а не ему.
- **Автотесты:**
  `test_signing.py::test_accountant_hands_offer_to_the_director`,

### E2E-04a. Контрпредложение другим продуктом

- **Роли:** клиент-директор (`clean@demo.local`, Лариса Тихонова, ООО «Городская химчистка»).
- **Шаги:** «Пополнить оборотные средства» → «Экспресс-оборот», 300 000 ₽, 12 мес.; выручку оставить как
  подставилась (1 млн) → отправить. Сравнить «вы просили → банк предлагает», принять, подписать кодом.
- **Ожидается:**
  - Статус «Есть предложение»: в сравнении строка «Продукт: Экспресс-оборот → Овердрафт», 150 000 ₽ на 12 мес.
    под 26,9 % (грейд B). Первая причина: «По продукту «Экспресс-оборот» условия не проходят даже на минимальную
    сумму — под ваши показатели подходит «Овердрафт»: 150 000 ₽ на 12 мес.». Почему: действующие платежи по
    кредитам (485 тыс. в месяц) съедают почти половину выручки. Посильность овердрафта считается как у
    кредита, гасимого за 12 мес., но его минимальная сумма ниже (100 тыс.), поэтому банк снижает сумму до
    150 тыс., при которых нагрузка не больше 50 %.
  - У овердрафта в месяц платятся только проценты: в сравнении «3 363 ₽ — только проценты», под ним — основной
    долг 150 000 ₽ возвращается в конце срока; в блоке подписания и на странице кредита — «Проценты в месяц».
    После выдачи: «Лимит овердрафта 150 000 ₽ открыт на расчётном счёте компании».
  - В договоре и в «Мои кредиты» — «Овердрафт», 150 000 ₽. На странице заявки после принятия блок «Условия
    кредита» и карточка в «Мои заявки» тоже показывают «Овердрафт», 150 тыс. ₽ на 12 мес.; запрошенное —
    строкой «Вы просили: Экспресс-оборот · 300 тыс. ₽ · 12 месяцев».
- **Автотесты:** `test_pipeline.py::test_heavy_existing_debt_gets_an_overdraft_instead`,
  `test_policy.py::test_other_product_is_offered_when_the_requested_one_does_not_fit`; в браузере —
  `e2e/tests/personas.spec.ts` (clean).

    причина «Выручка подтверждена только выпиской — сверьте её с оборотами по счёту», источник выручки — выписка.
  - Клиент видит «Одобрено»: 500 000 ₽ под 22,9 %. Открытых запросов нет, в журнале событие загрузки документа.
- **Автотест:** `test_pipeline.py::test_missing_tax_revenue_requests_statement_and_resumes`; в браузере —

## Отказоустойчивость

Эмулятор умеет «ронять» источники: `egrul`, `fns`, `bki`, `abs`, либо все сразу (`all`). Режимы: `error`
(источник отвечает 503) и `timeout` (зависает). Параметр `count` — сколько запросов сломать; без него источник
лежит, пока сбой не снят (`"mode":"none"`).

Bash / Git Bash:

```bash
# БКИ: короткий сбой — ответит ошибкой 3 раза (все попытки одного шага), дальше работает
curl -X POST localhost:8001/admin/faults -H "Content-Type: application/json" -d '{"source":"bki","mode":"error","count":3}'
# БКИ: лежит постоянно
curl -X POST localhost:8001/admin/faults -H "Content-Type: application/json" -d '{"source":"bki","mode":"error"}'
# АБС банка: лежит постоянно (для выдачи)
curl -X POST localhost:8001/admin/faults -H "Content-Type: application/json" -d '{"source":"abs","mode":"error"}'
# Снять все сбои
curl -X POST localhost:8001/admin/faults -H "Content-Type: application/json" -d '{"source":"all","mode":"none"}'
# Посмотреть текущие сбои
curl localhost:8001/admin/faults
```

Windows PowerShell (там `curl` — другая команда):

```powershell
Invoke-RestMethod -Method Post -Uri http://localhost:8001/admin/faults -ContentType 'application/json' -Body '{"source":"bki","mode":"error","count":3}'
Invoke-RestMethod -Method Post -Uri http://localhost:8001/admin/faults -ContentType 'application/json' -Body '{"source":"bki","mode":"error"}'
Invoke-RestMethod -Method Post -Uri http://localhost:8001/admin/faults -ContentType 'application/json' -Body '{"source":"abs","mode":"error"}'
Invoke-RestMethod -Method Post -Uri http://localhost:8001/admin/faults -ContentType 'application/json' -Body '{"source":"all","mode":"none"}'
Invoke-RestMethod -Uri http://localhost:8001/admin/faults
```

### Локальный запуск

```bash
cd backend
.venv/Scripts/python -m pytest -q          # все 144 теста; в Linux/macOS — .venv/bin/python
```

| `test_api.py` | вход, подбор продуктов, привязка компании, жизненный цикл заявки |
| `test_hardening.py` | идемпотентность, токены, поток статуса, права на компанию, падающий шаг |

### Что проверяет CI

Файл `.github/workflows/ci.yml`, запуск на каждый push в `main` и `feat/**` и на pull request. Три задания:

1. **backend** — PostgreSQL 16 как сервис; `alembic upgrade head` и `alembic check` (миграции применяются и
   совпадают с моделями); `python -m pytest -q` на схеме из миграций; сверка с кодом, каждая из них —
   `--check`, при расхождении падает:
   - `python -m scripts.export_openapi --check` — `docs/openapi.json`;
   - `python -m scripts.export_state_diagram --check` — диаграмма состояний в `docs/state-machine.md`;
   - `python -m scripts.export_collection --check` — коллекция запросов `docs/postman_collection.json`.
2. **frontend** — `npm ci` и `npm run build` (сборка и проверка типов).
3. **compose** — после двух первых, на чистом раннере ровно командой из README:
   - `docker compose up --build -d --wait` (ждёт healthcheck всех сервисов, включая «пульс» воркера);
   - дымовой сценарий через nginx `python3 scripts/smoke.py http://localhost:8080 --timeout 180`: проверка
     готовности `/health/ready`, демо-вход `bakery@`, заявка 3 000 000 ₽ на 12 мес., ожидание «Одобрено»;
   - коллекция запросов через newman (`e2e`, `npm run api`): папка «Сквозной сценарий: от заявки до выдачи»
     целиком, от входа до кредита с графиком;
   - сценарии в браузере (Playwright, `npm run ui`) для каждой демо-учётки из README: решения (одобрение,
     контрпредложение, в том числе другим продуктом, специалист, отказы), подпись кодом, выдача и график,
     кабинет аналитика (трасса, воспроизведение, решение, симулятор), лента новостей, сбой БКИ;
   - ресурсы стенда (`scripts/resource_report.py`): сразу после запуска стенда фоновый цикл раз в 2 секунды пишет
     `docker stats`; после полного прогона сценариев, даже если они упали, строится отчёт — пик памяти каждого
     контейнера (cgroup v2, `memory.peak`; если недоступен — максимум по замерам), максимум по замерам, сумма и
     наибольшая одновременная сумма, размеры образов (`docker compose images`), `docker system df`. Отчёт
     выводится в сводку задания (Actions → прогон → Summary) и сохраняется в артефакте `resources` (`resources.md`,
     `stats.log`, хранится 30 дней). Недостающий замер отчёт заменяет словами «нет данных» и задание не роняет;
   - запись основного сценария на видео — после всех проверок, поэтому их результаты не меняет: стенд пересоздаётся
     (`docker compose down -v`, затем `up -d --wait` без пересборки), и тест `e2e/tests/demo/main-scenario.spec.ts`
     (`npm run demo`, конфиг `playwright.demo.config.ts`, обычный `npm run ui` его не запускает) в одном окне, с паузой
     около 300 мс после каждого действия и короткими подписями на экране проходит путь клиента «Северной пекарни»:
     подбор → заявка с подставленными данными ЕГРЮЛ и ФНС → решение с причинами → договор и график → подпись кодом →
     «Деньги на счёте!» → страница кредита, затем вход аналитиком: очередь → карточка оценки и трасса правил →
     «Воспроизвести решение» → симулятор политики. Запись в артефакте `demo-video` (хранится 30 дней): mp4, если на
     раннере есть ffmpeg, иначе webm. Если сценарий упал, запись сохраняется всё равно;
   - при падении — отчёт Playwright и журналы сервисов; в конце `docker compose down -v`.

Команды сверки с кодом можно выполнить локально из папки `backend` (без `--check` файлы пересобираются).

### Что не покрыто автотестами

- В браузере не проверяются негативные и ролевые сценарии (NEG-…): они покрыты автотестами API.
- Точные значения сроков в реальном времени (7 и 14 дней) и пауза повтора выдачи (60 с) — в тестах сдвигаются
  даты в БД.
- Профили риска ИНН 5, 6, 8 и подключение произвольных ИНН через кабинет (см. E2E-13).
- Попытка аналитика одобрить заявку со сработавшим стоп-фактором (NEG-44).
- Повторный прогон `npm run ui` на уже использованном стенде: `new@` подключает ИНН один раз, поэтому
  сценарии в браузере запускаются на чистом стенде (`docker compose down -v`, затем `up`).
